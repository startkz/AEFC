# IOTJ-R3 — Rule-aware adaptive credibility attack / IEEE39 AC

## Versioning and claim boundary
Source branch: `experiment/iotj-76369-r3-adaptive-strength-20261110`, forked from `experiment/iotj-76369-ac-grid-bridge-20261102`.
The attacked implementation is **the existing utility--drift weighted sparse coordinator in `iotj_bridge/strict_agent.py`**, NOT the separate robust f-trimmed theorem in the later AEFC formulation. This experiment tests the weakness of that legacy scorer and independently labels the 0.20 cap as a mitigation, not an inherent guarantee. The physical backend is pandapower quasi-static AC; it is **not** a dynamic rotor-frequency experiment.

## Threat model and allowable observations
An adversary compromises the last M=2 of N=10 clients (IDs 8, 9) in IEEE39; corruption begins at federation round index 1, after one unmodified round. The adversary knows: the global shared backbone, prior published server-side prototype reference, previous global model increments, the current uploaded sparse candidate generated by **its own compromised client**, and that client's previous public aggregation weight and self-generated score. It does **not** know same-round honest sparse messages, individual honest utilities, honest prototypes, held-out test rewards, or AC future trajectories.

At every compromised upload, a deterministic, test-oracle-free search constructs candidate messages. The upload count and coordinate budget `k=ceil(0.2*d)` stay fixed; indices may change but cannot repeat or exceed dimension. Prototype *keys and lengths* remain fixed; values interpolate toward the previous broadcast center. Reported recovery utility increases up to the original server `cap_utility=1`. The update candidate is confined to a per-strength norm budget before the server's unchanged `clip_update=0.075`. The server independently validates every message, applies the same norm clipping and prototype clipping, and computes
`score = clip(utility,0,cap_utility) / (||clipped sparse update||+epsilon) * exp(-shift_lambda * prototype drift)`,
with `epsilon=0.001`. Intensity `lambda in {0.25,0.50,1,2}` scales the utility slack, reference-prototype blend and upload norm budget; due to server capping, values of 2 can saturate. `lambda=0` is a verified no-op unit-test control.

## Two attack goals, not interchangeable
- `adaptive_weight`: maximize a prior-only proxy for the *malicious client's accepted normalized weight* using the same score. This frequently favors very small/zero-norm messages and therefore need not damage recovery.
- `adaptive_damage`: maximize proxy accepted weight times an update deliberately opposed to the **previous public global direction**, never the current honest private update.
- `adaptive_meta`, `adaptive_update`, `adaptive_proto`: strength-1 component interventions. The fixed `joint` attack is maintained as a pre-existing non-optimized comparator; `clean` is the matched control.

The proxy for competing score mass is derived solely from the compromised client's previous self score and its **previous public normalized weight**; a declared fixed fallback is used in the first attack round. It is not a true oracle solution of the global maximization problem. Therefore, we describe the method as **discrete rule-aware adaptive search, not certified worst-case search**. Candidate count, predicted score, proxy objective, chosen norm, sparse support changes, actual score and accepted weight are logged.

## Complete frozen matrix
- Platform: IEEE 39-bus, N=10, M=2; heterogeneous observation setting `dim`.
- Defenses: uncapped original scorer; separately named `max_weight=0.20`.
- Independent training seeds: 90–94; 1000 training episodes each; 200 aggregation rounds (five episodes/round); 10 disjoint held-out evaluations per seed.
- Same model/control protocol as inherited strict full-budget experiments: `adv`, `batch=256`, `hidden=128`, `latent=32`, `local_steps=5`, `sharing_steps=2`, `kappa=0.2`, fixed application payloads.
- Scenarios per defense/seed: `clean`, `joint`; `adaptive_weight` and `adaptive_damage` each at 0.25,0.50,1,2; `adaptive_meta`, `adaptive_update`, `adaptive_proto` at 1. Total: 13 scenarios x 2 defenses x 5 seeds = **130 full-budget independent jobs**.
- Do not merge this scan with the previous M={0,1,2,3} coalition-size experiment. This scan fixes M=2.

## Outcome definition and attribution
For each seed and condition, evaluate the same previously frozen held-out schedule. Primary: mean final restored load (percent), mean recovery-time area (percent), safe dwell success /10, per-seed differences from the clean comparator **under the same defense**. Security telemetry: per-round acceptance of each malicious client, fraction accepted, sum of accepted malicious weights, individual scores and selected sparse support. Training seed (not episode, step or round) is the unit for uncertainty; 95% CIs bootstrap **five seed-level summaries**. Paired load decline (positive means attacked worse) and accepted weight must be reported separately; high weight does not imply large recovery damage.

## Independent audit / publication gating
The separate `iotj_bridge/audit_adaptive_strength.py` checks all 130 unique identities, manifest and checkpoint SHA256, 1000 episode/200 round/10 evaluation counts, scoring arithmetic, client acceptance, cap enforcement, prior-only search provenance, sparse support and attack intensity. A failed or partial matrix emits an explicit failure report and **never** creates results LaTeX or bilingual evidence-based replies. Only after all 130 pass does audit generate:
- `adaptive_per_seed.csv`
- `adaptive_per_round.csv`
- `adaptive_summary.csv`
- `AdaptiveStrengthResults.tex`
- `Reviewer_Adaptive_EN.md`, `Reviewer_Adaptive_ZH.md`
- `audit_report.json`

The raw per-run JSON, manifests and `.pt` checkpoints remain in versioned 90-day GitHub Actions artifacts. Full proof and reproducibility claims require checking source SHA, workflow run, dependencies and raw artifacts. IEEE118's saturated terminal objective will **not** be reused to infer effectiveness without a discriminating non-saturated recovery metric.

## Scientific limitation
The known weakness in the original client-report-weighted score is an **experimentally testable vulnerability**, not an established Byzantine robustness guarantee. No results are claimed before complete execution and audit. Strong intensity may saturate the upload clipping/utility cap, so a monotone damage trend is not assumed. Even strong attacks under the modeled constraints do not establish a global worst-case bound.
